# DZ1 — разбор: приватный AI-роутер по чувствительности

## Что построено
Чат-ассистент в `proshop_mern`: виджет (залогиненный юзер) → Express-прокси `POST /api/assistant/chat`
(добавляет доверенный `userId`/`token` из JWT) → **n8n-роутер**: regex-PII-детект → Switch **local/cloud**
→ AI Agent (Tools Agent) с **scoped HTTP-тулами** к БД магазина → запись в Mongo `chatlogs` → ответ.
Обе ветки — агент с инструментами `get_my_orders` / `get_profile` / `search_products`, скоуп по JWT из
вебхука. Локальная нога — Ollama `qwen3.5:4b` (через OpenAI-совместимый `/v1`), облачная — стаб на той же
модели (чтобы не тратить на OpenRouter; маршрут и учёт стоимости демонстрируются). Админ видит всё на
`/admin/assistant-logs`.

## Что уводит в локалку (демо, 8 запросов)
Маршрут решает **regex** по тексту сообщения:
- **EMAIL_ADDRESS** (`ivan@test.com`, `john@example.com`), **PHONE_NUMBER** (`+375291234567`),
  **CREDIT_CARD** (`4111 1111 1111 1111`) → **local**, стоимость **$0.00**, данные не покидают периметр.
- Чистые запросы (каталог, политика возврата, «что умеешь», «где мой заказ») → **cloud**.

В демо **4 из 8** ушли в local за **$0.00**; cloud-запросы получили оценку стоимости (~$0.00003–0.00008
каждый при стаб-цене). Экономия в абсолюте мала (модель дешёвая), но **суть приватности**: каждый PII-запрос
обрабатывается дома и не уезжает наружу.

## Почему роутеру не нужен GPU
Решение о маршруте — это **regex в Code-ноде** (микросекунды, CPU). Решение о маршруте всегда дешевле
работы, которую маршрутизируешь: классификация «есть PII / нет» на порядки дешевле полного ответа агента
(~5–13 с на 3060). Роутер лёгкий by design — GPU нужен только модели-процессору, и только под реальной
параллельной нагрузкой.

## «Подвох» (из THEORY-privacy-routing) — наблюдаем в демо
Запрос **#6 «Где мой последний заказ?»** не содержит PII в тексте → роутер отправил его в **cloud**. Но
агент вызвал `get_my_orders` и вернул **имя, адрес и состав заказа** — то есть приватные данные ушли в
облачную ветку **через ответ тула, уже ПОСЛЕ решения о маршруте**. Роутер по тексту чата закрывает лишь
верхушку: PII втекает в контекст из БД/тулов, RAG, файлов, памяти. По-взрослому это решают **роутингом по
намерению/тулу** (тул `get_my_orders` помечен `PII_SOURCE` → форсим локалку), **маскированием** (Presidio +
LiteLLM), **минимизацией полей** (локалка извлекает только `{order_id, status, eta}` для облака) и
**разделением плоскостей** (dual-LLM / CaMeL). В домашку это не входит, но именно сюда смотрит честная
приватность.

## Осознанные инженерные решения
- **Regex-only PII-детект** (без LLM-классификатора имён). LLM-классификатор имён в n8n с локальной
  thinking-моделью оказался и **непрактично медленным** (`/no_think` через OpenAI-ноду не долетает →
  ~10 мин на классификацию), и **неточным** (не ловил «Иван Петров»). Спека прямо разрешает regex-вариант.
  Цена: **имена** не уводятся в локалку (regex их не ловит) — это известное ограничение regex и, по иронии,
  ещё одна грань того же «подвоха» (защищать надо источник данных, а не текст).
- **Agent + native tools в n8n** оказался хрупким с локальной Ollama: пришлось пересоздавать AI-ноды
  нативно (импортный JSON ломал tool-execution), чинить paired-item (`.first()` вместо `.item` после
  LLM-нод) и брать модель через **`OpenAI Chat Model` → Ollama `/v1`** (нода Ollama не умеет
  function-calling). Рабочий итог — латентность ~5–13 с, корректная маршрутизация и ответы из БД.

## Итог
Роутер корректно развёл 8 запросов (4 local / 4 cloud), приватные = $0.00, ассистент отвечает из БД и
встречает по имени, всё видно в админ-дашборде. Полный лог — `demo-run.md`, скрин дашборда — в `demo/`.
